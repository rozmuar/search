# Архитектура системы

> Сверено с реальным кодом (`Dockerfile`, `nginx.conf`, `docker-compose.yml`, `src/api/main.py`) по текущей ветке `main`. Предыдущая версия описывала микросервисную архитектуру (отдельные API Gateway / Search Service / Indexer Service / Scheduler Service) — в реальности всё это один процесс.

## Общая картина

Это **монолит**: один FastAPI-процесс (`src/api/main.py`) обслуживает и приватный личный кабинет (JWT), и публичные поисковые эндпоинты для виджета (API-ключ), и фоновый планировщик обновления фидов — всё в одном asyncio event loop одного `uvicorn`-воркера.

```
┌──────────────────────────────────────────────────────────────────┐
│  Контейнер "api" (единственный сервис из docker-compose кроме БД) │
│  supervisord запускает два процесса:                              │
│                                                                    │
│  ┌───────────────┐   proxy_pass 127.0.0.1:8000   ┌─────────────┐ │
│  │  nginx :80/443 │ ─────────────────────────────▶│  uvicorn    │ │
│  │  - статика     │                                │  (1 worker) │ │
│  │    src/web/*   │                                │  FastAPI    │ │
│  │  - /embed.js   │                                │  app        │ │
│  │  - /api/* proxy│                                └──────┬──────┘ │
│  └───────────────┘                                        │        │
└─────────────────────────────────────────────────────────────┼──────┘
                                                                │
                                        ┌───────────────────────┼───────────────────────┐
                                        ▼                                               ▼
                                 ┌─────────────┐                                 ┌─────────────┐
                                 │    Redis    │                                 │  PostgreSQL │
                                 │ (индексы,   │                                 │ (users,     │
                                 │  аналитика, │                                 │  projects,  │
                                 │  статус     │                                 │  бэкап      │
                                 │  фидов)     │                                 │  товаров/   │
                                 └─────────────┘                                 │  аналитики) │
                                                                                  └─────────────┘
```

**Важное следствие "один воркер, один event loop":** любая синхронная CPU-тяжёлая работа внутри запроса блокирует **весь** сервер — не только текущий запрос. Это реальная проблема, с которой уже сталкивались (парсинг XML фида и построение индекса раньше выполнялись прямо в event loop и замораживали поиск/логин на время обработки фида; сейчас вынесены в `asyncio.to_thread`, см. [feed-processing.md](feed-processing.md)). При проектировании новых фич это стоит держать в голове.

## Что внутри FastAPI-приложения

Не отдельные сервисы, а модули одного процесса:

| Модуль | Роль |
|---|---|
| `src/api/main.py` | все HTTP-эндпоинты, `lifespan` (старт/стоп ресурсов) |
| `src/api/auth.py` | JWT, хеширование пароля (sha256 + статичная соль — не bcrypt/argon2) |
| `src/api/database.py` | пул PostgreSQL, DDL, CRUD пользователей/проектов/бэкапов |
| `src/api/storage.py` | `DataStore` — фасад над Redis+PostgreSQL для проектов/товаров-для-дашборда/аналитики |
| `src/search/engine_simple.py` | поиск (инвертированный индекс + n-граммы + синонимы + fallback раскладки) |
| `src/search/indexer_simple.py` | построение индекса при загрузке фида |
| `src/search/query_processor_simple.py` | нормализация, токенизация, RU/EN раскладка |
| `src/feed/parser.py` | скачивание + парсинг YML (Яндекс.Маркет) |
| `src/feed/scheduler.py` | фоновая задача, раз в 15 минут проверяет фиды старше 4 часов и обновляет их |

`src/search/engine.py`, `indexer.py`, `query_processor.py` (без `_simple`) и весь `src/ml/` — заготовки под ML-версию (см. [ml-integration.md](ml-integration.md)), в проде **не используются**. `src/core/config.py` тоже не импортируется приложением — мёртвый код.

## Запуск при старте (`lifespan` в `main.py`)

1. `db.connect()` — пул PostgreSQL + DDL/миграции (`CREATE TABLE IF NOT EXISTS`).
2. Подключение к Redis.
3. Инициализация `search_engine`, `indexer`, `data_store`, `feed_manager`.
4. Запуск планировщика автообновления фидов (`start_feed_scheduler`).
5. **В фоне** (`asyncio.create_task`, не блокирует запуск): восстановление товаров/индекса/аналитики из PostgreSQL для проектов, у которых пусто в Redis — см. [database.md](database.md#восстановление-после-потери-redis).

До недавнего времени шаг 5 выполнялся синхронно и мог надолго задержать момент, когда `uvicorn` начинает принимать соединения — при этом nginx уже проксировал на порт 8000, отдавая `502` всем запросам, включая логин. Сейчас вынесено в фон.

## Аутентификация и разграничение доступа

Два независимых уровня, не пересекаются:

- **Личный кабинет** — JWT в `Authorization: Bearer`, проверяется `require_auth`/`get_current_user` в `main.py`. Доступ к проекту — прямая проверка `project.user_id == current_user.id` в каждом эндпоинте (нет отдельного слоя авторизации/ролей).
- **Виджет** — API-ключ проекта (`X-API-Key` или `?api_key=`), без привязки к пользователю. Кэшируется в Redis (`apikey:{key} -> project_id`) поверх PostgreSQL как источника правды.

Нет rate limiting, нет RBAC/ролей внутри проекта (один владелец = один пользователь), нет audit log.

## Масштабирование — текущее состояние

Реально задеплоен один инстанс `api` (см. `docker-compose.yml`) — ни горизонтального масштабирования, ни Redis Cluster, ни балансировщика нет. `uvicorn` тоже поднят с одним воркером (`Dockerfile`: `uvicorn src.api.main:app --host 127.0.0.1 --port 8000`, без `--workers`). Схема "Load Balancer → API#1..N → Redis Cluster" из старой версии этого документа — нереализованный план, не текущее состояние.
